## 本周核心认知清单

- [x] 推理 vs 训练：训练是"建工厂"一次性投入，推理是"工厂运转"持续成本
- [x] 推理算力需求是训练的 3-10 倍——推理成本正在超过训练成本
- [x] 推理两大指标：延迟（TTFT，聊天敏感）vs 吞吐（总处理量，批处理敏感）
- [x] 延迟和吞吐往往不可兼得——出租车 vs 公交车的权衡
- [x] KV Cache 是推理内存核心——70B 模型 128K 上下文下 KV Cache（343GB）比模型参数还大
- [x] 量化：BF16→INT8→INT4，精度换吞吐。INT8 是甜点区（损失<3%，省4倍）
- [x] PTQ（训练后量化）vs QAT（量化感知训练）——JPEG 压缩类比
- [x] PagedAttention：分页管理 KV Cache，消除内存碎片，吞吐提升 2-4 倍
- [x] GQA：架构层面缩小 KV Cache 4-8 倍，现代模型标配
- [x] 投机解码：小模型草稿大模型验证，延迟改善 2-3 倍且不损精度
- [x] 蒸馏：大模型教小模型，成本降 10 倍，能力保 80%
- [x] token 经济学：GPU $2/小时 → 100万 token 成本约 $5.5
- [x] 推理成本 2 年降 10 倍——释放应用层需求
- [x] 推理集群 vs 训练集群：性价比优先、分散部署靠近用户
- [x] 推理时代赢家分散化：推理芯片、推理云服务、应用层受益
- [x] 组合优化叠加效应：INT8+GQA+PagedAttention+投机解码 ≈ 吞吐 10-20 倍
- [x] **延迟、吞吐、质量是三个独立的轴，不能互相代指**——量化降的是质量不是速度，蒸馏小模型更快但更笨
- [x] **"延迟 < 1 秒"只能指 TTFT**——100 token/秒下，2000 token 端到端要 20 秒，端到端 1 秒物理上不成立
- [x] **投机解码优化 TPOT，对 TTFT 几乎无帮助**——TTFT 要靠 prefill 侧优化（chunked prefill、prefix caching）
- [x] **投机解码的草稿模型通常就是蒸馏出来的**——同一技术放主模型要吞 20% 能力损失，放草稿模型被验证环节完全对冲
- [x] **PagedAttention 提吞吐的机制是加大 batch，会推高单请求延迟**——必须设 batch 上限，不是开到最大
- [x] **推理优化不是性能调优，是商业可行性的前置条件**——不叠优化，Llama 3 自部署年成本 $400 万而非 $73 万
- [x] **成本结构里占比最大的环节，是降本周期中被压缩的对象，不是受益者**
- [x] **垂直场景里检索质量的边际收益 > 模型能力的边际收益**——"订单为什么没发货"GPT-4 也答不了，它不知道你家数据

## 形成的判断框架

### 框架 21：性能需求的三轴分解

> 任何"要快"的需求都必须先拆成三个独立的轴——**延迟**（单个请求多久有反应）、**吞吐**（单位时间总处理量）、**质量**（答得对不对）。这三者不能互相代指，而且常常互相对冲：加大批次提吞吐会推高延迟，量化降成本会损质量。

更进一步，"延迟"本身还要再拆：**TTFT**（首字延迟，由 prefill 阶段决定）和 **TPOT**（每 token 输出时间，由 decode 阶段决定）。优化手段各管一端——投机解码改善 TPOT，对 TTFT 无效。没拆到这一层，就会把优化资源投在错误的阶段。

**应用场景**：所有性能需求的澄清。听到"要快"、"要流畅"、"用户等不及"，第一反应不是去优化，是先问"快在哪个轴上"。

### 框架 22：降本红利的分配规律

> 一个产业经历大幅降本时，受益最大的**不是成本结构中占比最大的环节**——那恰恰是降本的刀首先砍向的对象。受益最大的是**因成本下降而解锁了全新需求的下游**：它的变化是从"算不过账所以做不了"到"做得了"的 0→1 质变，而上游的变化只是"很好→还行"的边际量变。

同时要区分**绝对收入**与**相对地位**：杰文斯悖论（Jevons Paradox）下，单位成本下降会放大总消耗量，上游的绝对营收完全可能继续上涨——但议价能力和份额在下降。讨论"谁受益最大"是相对排序问题，不能用绝对数回答。

**受损最大的永远不是被降本压缩的龙头**（它还有生态和其他市场），**而是只赚价差、不创造增量价值的中间层**——成本降 10 倍，售价也降 10 倍，价差直接被抹平。

**应用场景**：任何技术降本周期的产业链判断。也适用于反推——想知道降本会从哪里挤出来，先看成本结构里谁占比最大。

### 框架 23：同一技术在不同位置的风险不对称

> 一项有缺陷的技术，风险大小取决于它在系统中的**位置**，而不是它本身的缺陷有多大。蒸馏小模型有 20% 的能力损失：放在**主模型**位置，这 20% 直接变成用户看到的错误答案；放在**草稿模型**位置（投机解码），猜错由大模型兜底，精度损失为零。

判断依据是：**这个环节的输出有没有下游校验**。有校验，缺陷被吸收；没校验，缺陷直达用户。

**应用场景**：技术选型时"这个方案不够好所以不用"的草率否决。正确的问法是"它够好到能放在哪个位置"——便宜但不可靠的组件，放在有兜底的位置上就是免费的性能。
